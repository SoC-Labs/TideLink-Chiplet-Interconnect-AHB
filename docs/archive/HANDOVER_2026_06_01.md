## 2. What's broken

### 2.1 Doorbell delivery on canonical role assignment

Persistent across Builds #4 through #10. Symptom matrix:

| Step | Pre-ring | After M→S 100 rings | After S→M 100 rings |
|---|---|---|---|
| Lane lock | 0xff both | 0xff both | 0xff both |
| FCSM state | **4 (LINK_IDLE)** | **4 (LINK_IDLE)** | **4 (LINK_IDLE)** |
| cr_pkt_seen | 1 both | 1 both | 1 both |
| crack_pkt_seen | 1 both | 1 both | 1 both |
| Master returner_busy | 0 | **1** (wedged) | 1 |
| Slave returner_busy | 0 | 0 | **1** (wedged) |
| Slave DB_RESP | 0 | **0** (no delivery) | n/a |
| Master DB_RESP | 0 | n/a | **0** (no delivery) |

**Critical correction to all prior analysis**: my HW reads used `(REG_STATUS >> 4) & 0x7` for FCSM — wrong register and wrong bits. Correct is `(LANE_STATUS >> 17) & 0xF`. With the correct decode, **FCSM stays at state 4 (LINK_IDLE)** before AND after the wedge, on both master and slave. **The FSM never even attempts to enter LINK_DATA.**

In simulation, the failing test shows `m_state=5 s_state=7` — master at LINK_DATA tx-blocked, slave at SEND_NACK. **This is NOT what HW shows.** The HW wedge happens BEFORE the FCSM gets involved.

### 2.2 What this means for prior bug hypotheses

| Layer | Sim shows | HW shows | Implication |
|---|---|---|---|
| PHY (lane lock, cal_done) | ✓ | ✓ | Healthy, unchanged before/during/after wedge |
| Credit handshake (cr/crack) | ✓ | ✓ | Bilateral, complete |
| Credit ledger (`fe_rx_credit_max`) | ✓ populates to `0x1f` | (no HW probe) | Probably ✓ — see Bug C forensic |
| FCSM TX path (state 4→5) | wedges at 5 (sim's Bug C path) | **NEVER ADVANCES from 4** | **The wedge is upstream of the FCSM** |
| Slave RX framer (NACK decode) | wedges at state 7 in sim | (slave never sees data — master doesn't TX) | L9/L9b cannot help in HW |
| Returner busy bit | (not sim-modeled in detail) | sets to 1 on doorbell write, never clears | **Returner accepts doorbell but never propagates** |

**All four prior fix attempts (F-1, F-1.5, F-2, L9, L9b) targeted the slave RX framer NACK decode.** The HW data shows the bug is in the doorbell → returner → FC adapter path — entirely different RTL locus. None of this session's RTL fixes touch the actual HW failure path.

### 2.3 Locus narrowed to: `src/rtl/fifo/tidelink_returner.sv` + APB doorbell write path

The APB doorbell register at `0x014` (`REG_DOORBELL_TRIG` per `src/rtl/fifo/tidelink_apb_regs.sv:115`) is a W1C self-clearing pulse. The pulse must travel through:

1. APB regs → returner trigger
2. Returner → FC adapter sideband path
3. FC adapter → FCSM TX request (would cause state 4 → 5 transition)
4. FCSM TX → Wlink LL_TX → master GPIO → slave GPIO → slave LL_RX → slave FCSM → slave returner → slave DB_RESP_ACC increment

We observe step 1 happens (returner_busy=1) but step 3 never happens (FCSM stays at 4). So the bug is in **step 2** — the returner doesn't push the request through to the FC adapter, OR the FC adapter doesn't accept it, OR there's a sideband-grant arbitration issue.

## 8. The "is the link being trained and locked correctly during transfers?" question

**Answer: yes at the PHY layer, no advancement at the FCSM layer, wedge in between.**

Detail:
- **PHY lane lock**: stable at 0xff throughout the entire pre/during/post ring cycle. The 8 lanes never lose lock.
- **PHY cal_done**: 1 on both sides, doesn't toggle.
- **Link-layer credit handshake**: cr_pkt_seen=1 and crack_pkt_seen=1 on both sides, before and after rings. The handshake is observed and latched.
- **FCSM state**: stays at 4 (LINK_IDLE) on both sides. **Never transitions to 5 (LINK_DATA)** even when master's returner has been busy=1 for the entire post-ring period.
- **Returner level**: master's returner_busy goes from 0 to 1 on first doorbell ring, then never returns to 0. Same for slave on its own ring.

So the doorbell write IS reaching the returner (busy bit sets) but the returner is not propagating the request through to the FCSM. The FCSM doesn't see a TX request and stays idle. The PHY is fine because there's no traffic to corrupt — there's no traffic at all.

This is a **completely different bug locus** from everything analyzed in this session. The session memory entries about "slave RX framer NACK decode" describe the SIM symptom, which the cocotb model exhibits but HW does not.
