# TideLink PTP Protocol Specification

This document specifies the single-phase Precision Time Protocol (PTP) used by TideLink for clock synchronisation between chiplets over the die-to-die link.

## Overview

TideLink PTP implements a simplified two-message clock synchronisation protocol inspired by IEEE 1588. A Grandmaster chiplet (typically Ethernet-connected with access to an external PTP time source) synchronises one or more Subordinate chiplets via dedicated Wlink short packets over the die-to-die link.

The protocol uses hardware timestamp capture at the short packet handshake boundary, combined with idle gating of the Wlink TX link layer, to achieve low-jitter timestamps without requiring follow-up messages.

### Key Properties

- **Two-message exchange**: SYNC + DELAY_REQ (no follow-up messages required)
- **Hardware timestamp capture**: PHC `hw_capture` triggered at short packet TX/RX handshake
- **Idle-gated TX**: `tx_router_idle` signal gates PTP TX to eliminate link-layer jitter on transmit timestamps
- **Wlink short packets**: data_id=0x50 (SYNC), data_id=0x51 (DELAY_REQ), 32 bits on wire
- **No FC overhead**: bypasses FC state machine (no credits, replay, CRC) — 67% bandwidth reduction vs long packets
- **Software servo loop**: offset/delay computation and clock discipline performed in software

## Short Packet Format

PTP uses Wlink short packets (32 bits on the die-to-die link):

```
 31      24  23                 8  7              0
┌──────────┬────────────────────┬─────────────────┐
│   ECC    │     payload        │    data_id      │
│ (8 bits) │    (16 bits)       │   (8 bits)      │
└──────────┴────────────────────┴─────────────────┘
  Hamming     seq num / metadata   0x50 or 0x51
  SEC/DED
```

The message type is encoded directly in the `data_id` field, eliminating the need for a separate msg_type field within the payload. The 16-bit payload carries an optional sequence number or is set to zero.

### Message Types

| data_id | Name | Direction | Payload |
|---------|------|-----------|---------|
| 0x50 | SYNC | Grandmaster -> Subordinate | Sequence number (16-bit) or 0x0 |
| 0x51 | DELAY_REQ | Subordinate -> Grandmaster | Sequence number (16-bit) or 0x0 |

## Timestamp Capture Mechanism

### PHC Hardware Capture

The PTP Hardware Clock (PHC) provides a `hw_capture` input port. When asserted for one cycle, the PHC latches the current time into the HW_CAP register bank:

| Offset | Register | Description |
|--------|----------|-------------|
| 0x040 | HW_CAP_SEC_HI | Captured seconds [47:32] |
| 0x044 | HW_CAP_SEC_LO | Captured seconds [31:0] |
| 0x048 | HW_CAP_NS | Captured nanoseconds [29:0] |
| 0x04C | HW_CAP_NS_FRAC | Captured sub-nanosecond fraction [31:0] |

The `hw_capture` pulse is generated by the `tidelink_ptp` module at the moment the short packet TX/RX handshake completes (both TX and RX paths).

### Idle Gating for Jitter-Free TX Timestamps

The Wlink TX link layer introduces variable latency as packets from multiple sources are arbitrated and serialised. To eliminate this jitter on transmit timestamps:

1. `tidelink_ptp` monitors the `tx_router_idle` signal from the Wlink TX link layer
2. PTP TX is held until `tx_router_idle` is asserted (no other traffic in the TX pipeline)
3. The short packet TX valid is asserted simultaneously with the `hw_capture` pulse
4. Since the TX router is idle, the short packet enters the link layer with deterministic latency

This ensures that t1 (Grandmaster TX) and t3 (Subordinate TX) timestamps are captured with minimal jitter relative to the actual wire transmission.

## Protocol Flow

### Timing Diagram

```
    Grandmaster                    Die-to-Die Link               Subordinate
    ===========                    ===============               ===========

    [1] Wait for tx_router_idle
        Assert hw_capture ─► t1
        Send SYNC ──────────────────────────────────────────────►
                                                          hw_capture ─► t2
                                                          Receive SYNC [2]

                                                          [3] Wait for tx_router_idle
                                                              Assert hw_capture ─► t3
                                   ◄──────────────────────────── Send DELAY_REQ
    hw_capture ─► t4
    Receive DELAY_REQ [4]

    [5] Software reads t1, t4 from PHC HW_CAP registers
        Sends t1 to Subordinate (via mailbox FIFO or AHB bridge)

    [6] Subordinate reads t2, t3 from PHC HW_CAP registers
        Receives t1 from Grandmaster
        Computes offset and delay
        Adjusts local PHC
```

### Step-by-Step

1. **Grandmaster sends SYNC**: Software writes to the PTP AHB slave with msg_type=0x0. The `tidelink_ptp` module waits for `tx_router_idle`, then simultaneously asserts `hw_capture` (capturing t1 in the PHC) and drives the SYNC short packet (data_id=0x50) onto the Wlink TX path.

2. **Subordinate receives SYNC**: The Wlink RX path delivers the SYNC short packet to the PTP module. The `tidelink_ptp` module asserts `hw_capture` on receipt, capturing t2 in the Subordinate's PHC. The `ptp_irq` interrupt fires.

3. **Subordinate sends DELAY_REQ**: Software writes to the PTP AHB slave with msg_type=0x1. The module waits for `tx_router_idle`, captures t3, and sends DELAY_REQ short packet (data_id=0x51).

4. **Grandmaster receives DELAY_REQ**: The module captures t4 in the Grandmaster's PHC. The `ptp_irq` interrupt fires.

5. **Timestamp exchange**: The Grandmaster sends t1 to the Subordinate using either the mailbox FIFO (Path 2) or a transparent AHB write (Path 1).

6. **Offset and delay computation**: The Subordinate computes:

```
offset = ((t2 - t1) - (t4 - t3)) / 2
delay  = ((t2 - t1) + (t4 - t3)) / 2
```

Where:
- `offset` is the clock phase difference (positive means Subordinate is ahead)
- `delay` is the one-way propagation delay through the die-to-die link

## Clock Discipline

### Phase Correction

For large offsets (initial synchronisation), write the corrected time directly to the PHC using the SET_TIME registers. This provides an immediate step correction.

### Frequency Steering

For ongoing fine adjustment, modify the PHC's `NS_INCR_FRAC` register. This adjusts the fractional nanosecond increment applied each clock cycle, effectively steering the clock frequency:

- Increase `NS_INCR_FRAC` to speed up the clock (Subordinate is behind)
- Decrease `NS_INCR_FRAC` to slow down the clock (Subordinate is ahead)

The servo loop that maps computed offsets to `NS_INCR_FRAC` adjustments is implemented in software (Tier 1 servo). A typical PI controller approach is recommended.

### Steady-State Operation

In steady state, the software periodically triggers SYNC exchanges (e.g. every 100 ms to 1 s), computes offset, and applies a proportional-integral correction to `NS_INCR_FRAC`. The SET_TIME path is only used during initial lock or after large disturbances.

## Hardware Sync Initiator

The `tidelink_ptp` module includes an optional **hardware sync initiator** that autonomously generates periodic SYNC messages without CPU intervention. This mirrors IEEE 1588 Ethernet PTP, where `logSyncInterval` ranges from -7 (128 Hz) to +4 (1/16 Hz), with a default of 0 (1 Hz).

### Overview

The hardware sync initiator:
- Uses the PHC `nanoseconds` and `seconds` time outputs to determine when to fire
- Maintains a target timestamp that advances by a configurable interval after each SYNC
- Auto-increments a 16-bit sequence number in the SYNC payload
- Shares the TX path with software-initiated messages (software has priority)
- Is controlled via three dedicated registers in APB Region 2 (offsets 0x040–0x048)

### PHC Time Inputs

The hardware sync initiator requires the PHC time outputs to be wired into `tidelink_top`:

| Port | Direction | Width | Description |
|------|-----------|-------|-------------|
| `phc_nanoseconds` | Input | 30 | Current PHC nanoseconds counter |
| `phc_seconds` | Input | 48 | Current PHC seconds counter |
| `phc_pps` | Input | 1 | Pulse-per-second from PHC (reserved for future use) |

### Timing Diagram

```
    PHC Time         HW Sync FSM            FC TX

    t=0 ns           IDLE
    Enable written →  ARMED (target = t + interval)
    ...
    t=interval       Time reached → FIRE
                      Inject SYNC →        ──► SYNC (seq=0)
                      Wait TX done → ARMED (target += interval)
    ...
    t=2×interval     Time reached → FIRE
                      Inject SYNC →        ──► SYNC (seq=1)
                      Wait TX done → ARMED (target += interval)
```

### FSM States

| State | Description |
|-------|-------------|
| `HW_SYNC_IDLE` | Disabled. Transitions to ARMED on `hw_sync_en` rising edge. |
| `HW_SYNC_ARMED` | Comparing PHC time against target. Fires when `{seconds, ns} >= target`. |
| `HW_SYNC_FIRE` | Waiting for TX FSM to be idle. Injects SYNC with auto-incremented seq_num. |
| `HW_SYNC_WAIT_TX` | Waiting for TX FSM to complete. Advances target and increments seq_num. |

### TX Path Arbitration

The hardware initiator shares the TX path with software AHB writes:
- Software AHB writes always have priority (if both trigger on the same cycle, AHB wins)
- The hardware initiator retries on the next cycle if pre-empted
- The AHB slave stalls normally during hardware-initiated TX (hreadyout=0)

### Interval Configuration

The sync interval is configured in nanoseconds via the `HW_SYNC_INTERVAL` register. The initiator handles nanosecond rollover at 1,000,000,000 (second boundary) automatically.

| Interval | Rate | Use Case |
|----------|------|----------|
| 7,812,500 | 128 Hz | Fast convergence during initial lock |
| 125,000,000 | 8 Hz | Active servo tracking |
| 1,000,000,000 | 1 Hz | Steady-state maintenance (default) |

## Two-Level PTP Hierarchy

In the reference nanosoc-chiplet-tech deployment:

```
    IEEE 1588 PTP                TideLink PTP
    (Ethernet)                   (Die-to-Die)

    PTP Grandmaster
         │
         │  Ethernet 1588
         ▼
    Chiplet A (Grandmaster)  ◄──── Ethernet-connected
         │
         │  TideLink PTP (short packets 0x50/0x51)
         ▼
    Chiplet B (Subordinate)  ◄──── No Ethernet
```

- **Level 1**: Chiplet A synchronises to an external PTP Grandmaster via standard IEEE 1588 over Ethernet.
- **Level 2**: Chiplet B synchronises to Chiplet A via TideLink PTP over the die-to-die link.

This provides a hierarchical time distribution where all chiplets in the system share a common time reference, even if only one chiplet has direct Ethernet connectivity.

## TideLink PTP Registers

The PTP subsystem adds registers to the TideLink APB register block:

**Region 1 — Basic PTP (APB offsets 0x034–0x03C):**

| Offset | Name | Access | Description |
|--------|------|--------|-------------|
| 0x034 | PTP_CTRL | RW | Bit 0: PTP enable. When set, the PTP FC node is active. |
| 0x038 | PTP_RX_PAYLOAD | RO | Last received PTP packet payload [31:0]. Read-to-clear. |
| 0x03C | PTP_STATUS | RO | Bit 0: RX packet available. Bit 1: TX busy (waiting for idle). |

**Region 2 — HW Sync Initiator (APB offsets 0x040–0x048):**

| Offset | Name | Access | Description |
|--------|------|--------|-------------|
| 0x040 | HW_SYNC_CTRL | RW | Bit 0: HW sync enable. Bit 1: sequence number clear (W1C). |
| 0x044 | HW_SYNC_INTERVAL | RW | Sync interval in nanoseconds [29:0]. Default: 999,999,999 (~1 Hz). |
| 0x048 | HW_SYNC_STATUS | RO | Bit 0: active. Bit 1: busy (TX in progress). Bits [17:2]: sequence number [15:0]. |

### PHC HW_CAP Registers (in PHC register space)

| Offset | Name | Access | Description |
|--------|------|--------|-------------|
| 0x040 | HW_CAP_SEC_HI | RO | Hardware-captured seconds [47:32] |
| 0x044 | HW_CAP_SEC_LO | RO | Hardware-captured seconds [31:0] |
| 0x048 | HW_CAP_NS | RO | Hardware-captured nanoseconds [29:0] |
| 0x04C | HW_CAP_NS_FRAC | RO | Hardware-captured sub-nanosecond fraction [31:0] |

## Software Driver Flow

### Initialisation

```
1. Initialise PHC:
   a. Write NS_INCR and NS_INCR_FRAC for nominal clock period
   b. Set initial time via SET_TIME registers
   c. Enable PHC (CTRL.EN = 1)

2. Initialise PTP:
   a. Enable PTP subsystem: write 1 to PTP_CTRL[0]
   b. Enable ptp_irq in the interrupt controller

3. (Optional) Enable Hardware Sync Initiator:
   a. Write desired interval (ns) to HW_SYNC_INTERVAL (0x044)
   b. Write 1 to HW_SYNC_CTRL[0] (0x040) to enable
   → SYNC messages will be generated autonomously at the configured interval
```

### SYNC Exchange (Grandmaster Side)

```
1. Write SYNC message to PTP AHB slave (msg_type=0x0)
   → Module waits for tx_router_idle, captures t1, sends SYNC

2. Wait for ptp_irq (DELAY_REQ received)
   → t4 is captured automatically

3. Read t1 and t4 from PHC HW_CAP registers (0x040-0x04C)
   Note: read t1 first (before DELAY_REQ arrives) or use
   a second capture if contention is a concern

4. Send t1 to Subordinate via mailbox FIFO or AHB bridge
```

### SYNC Exchange (Subordinate Side)

```
1. Wait for ptp_irq (SYNC received)
   → t2 is captured automatically

2. Read t2 from PHC HW_CAP registers (0x040-0x04C)

3. Write DELAY_REQ to PTP AHB slave (msg_type=0x1)
   → Module waits for tx_router_idle, captures t3, sends DELAY_REQ

4. Read t3 from PHC HW_CAP registers (0x040-0x04C)

5. Receive t1 from Grandmaster (via mailbox FIFO or AHB bridge)

6. Compute:
   offset = ((t2 - t1) - (t4 - t3)) / 2
   delay  = ((t2 - t1) + (t4 - t3)) / 2

7. Apply correction:
   - Large offset: SET_TIME (phase step)
   - Small offset: adjust NS_INCR_FRAC (frequency steering)
```

### Interrupt Handling

```
ptp_irq handler:
  1. Read PTP_STATUS to determine event type
  2. If RX packet available:
     a. Read PTP_RX_PAYLOAD for message type and payload
     b. Read PHC HW_CAP registers for captured timestamp
     c. Signal software state machine (SYNC received or DELAY_REQ received)
```

## Limitations

1. **Idle gating wait time**: PTP TX is held until `tx_router_idle` asserts. If other sources (AXI, mailbox) are actively transmitting, the wait time is variable and unbounded in the worst case. This adds latency to the exchange but does not affect timestamp accuracy (the timestamp is captured at the actual TX moment).

2. **RX-side jitter**: The Wlink RX pipeline (deserialiser, link layer, short packet demux) introduces variable latency that is not gated. The t2 and t4 timestamps include this jitter. This is a fundamental limitation of capturing timestamps at the link layer interface rather than at the PHY. Note: short packets bypass the FC replay buffer, providing tighter RX timing than long packets.

3. **Software servo loop (Tier 1)**: The offset computation and clock discipline are performed entirely in software. This limits the servo bandwidth and adds interrupt/scheduling jitter to the control loop. A hardware servo (Tier 2) would improve steady-state performance.

4. **HW_CAP register contention**: The PHC has a single HW_CAP register bank. If a second `hw_capture` event occurs before software reads the first captured timestamp, the first value is overwritten.

5. **No flow control**: Short packets have no ACK/NACK, credits, or replay buffer. A corrupted packet (detected by ECC) is silently dropped. The PTP protocol handles this gracefully — a missed SYNC or DELAY_REQ simply means one skipped synchronisation interval.

5. **Single Subordinate per link**: The current protocol assumes a point-to-point topology. Multi-drop configurations would require message addressing and arbitration extensions.

6. **HW sync initiator shares TX path**: The hardware sync initiator uses the same TX FSM as software-initiated messages. If software writes to the PTP AHB slave while a hardware SYNC is pending, the AHB write takes priority. The hardware SYNC retries after the software TX completes, which may cause slight interval jitter.
