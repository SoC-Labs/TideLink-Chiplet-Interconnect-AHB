# MVP SCOPE DECISION — TideLink research chip, one-week deadline (2026-08-13)

**Vehicle:** KR260 two-board eth-chiplet pair (die_a = kr260_01 `10.22.24.159`,
die_b = kr260_02 `10.22.24.153`).
**Branch:** `integ/tidelink-consolidated-2026-08-07` @ `d317c98`.
**Status of this document:** decision aid. Read-only analysis; nothing committed.

## The bar, restated as three tests

The owner's bar — *"works most of the time and is recoverable"* — is not "all bugs
closed". It decomposes into three independent tests, and a bug is MVP-blocking only
if it fails one of them:

| # | Test | What threatens it |
|---|---|---|
| **1** | **WORKS MOST OF THE TIME** — link comes up and carries data on a high fraction of attempts | the **bring-up lottery**, regardless of bug count |
| **2** | **RECOVERABLE** — every failure has a way back **without a bench trip** | a wedge with no remote recovery path |
| **3** | **SMALL BUGS OK, SILENT CORRUPTION NOT** — cosmetic/obs/rare-corner bugs ship; data-integrity bugs do not | anything that returns success for data that did not land |

Everything below is sorted against those three tests and nothing else.

## 0. FOUR CORRECTIONS TO THE PREMISE — read these first

These change the scope decision materially. Each is stated with its evidence so it
can be checked rather than believed.

### C1. The "8 failing hold endpoints in `gpiorx_*` / `u_rmii_to_mii`" claim is WRONG

`imp/hw_gate/TL042_RUN1_VOID_2026_08_13.md:57-60` states the routed report shows
8 failing hold endpoints "all in `phy/gpio/gpiorx_*` (source-synchronous RX capture)
and `u_rmii_to_mii` — the known placement-varying hold race behind the bring-up
lottery." **The report does not say that.**

`imp/fpga/output/kr260-eth-chiplet/tidelink_design_wrapper_timing_summary_routed.rpt`:

```
WNS(ns)  TNS(ns)  TNS Fail  Total     WHS(ns)   THS(ns)    THS Fail  Total
 0.273    0.000      0      117821   -23.163  -185.070        8      117821
```

All 8 failing hold endpoints are `phy/gpio/gpiotx_N/g_pad_iob.io_pad_q_reg/C` →
`pad_tx[N]`, path group **`pad_clk_tx_fwd`**, slack −23.108 … −23.163 ns. They are an
artifact of `set_output_delay -min -20.000` on `pad_tx[*]`
(`fpga/targets/kr260-eth-chiplet/kr260_eth_chiplet_tidelink_timing.xdc:201`) — the
forwarded-TX-clock class already documented as benign in TL-009's own signoff walk-back.
**This is a −20 ns constraint value showing up as a −23 ns violation, not a real race.**

The RX capture domain in the *same* report **passes**:

```
Intra Clock  pad_clk_rx   WNS +0.273  0 fail /736   WHS +0.055  0 fail /736
```

**Consequence:** do not cite the timing report as evidence for the lottery. It is not.
But — see C2 — that does not mean the lottery is not a capture-clock problem.

### C2. The lottery IS a capture-clock problem, and STA cannot see it — but the fix is identified and is NOT enabled on this target

`fpga/docs/KR260_CAPTURE_CLOCK_TREE.md` is the canonical root cause:

> The 8 per-lane RX capture mux chains are lane-identical by construction … Vivado
> legally **merges** them into one LUT and drives all 8 lanes' capture flops from its
> output — a **fanout-372 general-routing** net. Its placement varies every build →
> few-hundred-ps inter-lane capture-clock skew → the all-lanes-AND SYNC commit gate
> turns that into a **bring-up lottery** … the capture-clock defect is *not* detectable
> from WNS/WHS.

That structure is **still present** in the shipping eth-chiplet netlist. From
`imp/fpga/project/kr260-eth-chiplet/tidelink_project.runs/impl_1/tidelink_design_wrapper_clock_utilization_routed.rpt`:

- capture clock passes through `LUT2 phy/g_word_pin_auto.wpa_gap_q[3]_i_4/O`, then a
  Vivado-inserted `BUFGCE_X0Y62` with **372 clock loads**;
- it is **split across two buffers from one source** — `BUFGCE_X0Y62` (372 loads) *and*
  `BUFGCE_X0Y51` (124 loads);
- measured insertion delay to two lanes' capture flops in the same report:
  **5.360 ns vs 6.113 ns**.

The fix exists in RTL (`2c32c2b`, parameter `USE_SHARED_CAP_BUFG`, measured on z2:
inter-lane capture skew **1.781 ns → 0.244 ns, 7.3×**, driver LUT2 → BUFG). It is
**off on kr260-eth-chiplet**, and the reason is precise: the eth-chiplet instantiates
`soclabs.org:user:nanosoc_eth_chiplet_vivado_wrapper:1.0`, and
`fpga/vivado_ip/nanosoc_eth_chiplet_vivado_wrapper.v` declares **only** `NUM_PHY_LANES`
and `DEVICE_CLASS`. There is no `USE_CLKBUF` port on it at all, so
`src/rtl/tidelink_top.sv:68` `USE_CLKBUF = 1'b0` applies and the generate branch never
elaborates. Grep of the routed reports for `u_rxclk_buf` / `u_cap_bufg` /
`g_shared_cap_bufg` returns **0**.

The contrast is the whole argument: `kr260-pair-onchip` **does** carry a real
`u_rxclk_bufg`, scores **WHS +0.010 / 0 failing endpoints**, and has its bring-up
lottery recorded as **GONE** (`docs/AUTONOMY_STATUS_2026_07_24.md:15`).

### C3. The harness's "0/16 single peer write" is an instrument artifact, not data loss

Step 6 of `imp/hw_gate/tl035_ab.sh` — self-labelled *"the honest delivery check"* —
reports `shared_sram_0[0x2D001000] = 0x00000000 … [FAIL]` in **16 of 16 runs, on every
build including the known-good baseline**. That is not a DUT defect. The harness starts
the receiver **before** the sender:

```
bash "$RUN" xfer_recv > 06_recv_b.log &   # die_b
rb=$!
sleep 3
bash "$RUN" xfer_send > 06_send_a.log     # die_a, 3 s LATER
```

and `do_recv` (`pynq_host/scripts/kr260_eth_xfer.py:201-213`) performs a **single
immediate read with no polling**. The read lands ~3 s before the write.

Proof it is not real data loss: in the *same run*, at the *same address*, the
localmem verify reads **16/16 byte-exact** —
`imp/hw_gate/control_baseline/tl035_baseline/06e_localmem_pre.log`:
`pre_inject DUMP base=0x2D001000 n=32 a5a50000 a5a50001 …`.

**This is the "verify the instrument before theorising about the DUT" trap, live.**
A 100 %-reproducible, build-independent failure sitting next to a same-address success
is an instrument signature, not a defect signature. Fix the ordering before anyone
reads 0/16 as a data-integrity finding.

### C4. Two registry entries are stale in the *safe* direction

- **TL-033** ("no credit-underflow protection — silent credit corruption", `status: open`,

- **TL-027** ("a2l data-plane replay nodes `_1/_3/_5` ship UNFIXED", `status: root_caused`,
  and "the override is NOT wired into any shipping flist") — **it is wired in.** Commit
  `8104b1e` re-pointed `flists/tidelink_fpga_v2.flist:269/:281/:284` at
  `src/rtl/local_overrides/WlinkGenericFCReplayV2_{1,3,5}.v`, and this is present in the
  HW-proven baseline build. The eye-gated handover's **lever 1** — the single

Also worth flagging for the record: `TL042_HW_RESULT_REJECTED_2026_08_13.md:15-16` claims

## 1. MUST-FIX FOR MVP

Four items. One touches the netlist; three are scripts/tests. Nothing else on the
34-item registry meets the bar.

### M1 — Enable the capture-clock BUFG hoist on `kr260-eth-chiplet` `[BAR 1]`

*Justification:* the bring-up lottery is the single largest threat to "works most of
the time", and this is the one lever with a measured effect on it (7.3× tighter
inter-lane capture skew on z2; lottery recorded **GONE** on the on-chip vehicle that
has this buffer). The eth-chiplet does not have it, and the reason is a missing
parameter on one IP wrapper, not a design problem.

*Work:* add `USE_CLKBUF` (which defaults `USE_SHARED_CAP_BUFG`) to
`fpga/vivado_ip/nanosoc_eth_chiplet_vivado_wrapper.v`; set `CONFIG.USE_CLKBUF 1` in
`fpga/targets/kr260-eth-chiplet/tidelink_design.tcl`; rebuild; **verify structurally**
with the existing `fpga/docs/verify_capture_clock_kr260.tcl` (exit 0 iff the capture
clock's driver ref-name is `BUFG*`).

*Effort:* ~0.5 day of edits, one build (~2–3 h), one bench session for the A/B.

*Risk:* **MEDIUM.** Netlist-affecting and never HW-validated on this target. Three
specific traps, all already documented:
- **Do NOT use `USE_CAP_CLKBUF`** (`83a531b`/`bccd96f`) — rejected; it bypasses the
  `io_pol` mux, inverts the mid-cell sample, and **kills the link**.
- **A `-verilog_define` will not reach packaged-IP OOC synth.** This must be a
  *parameter* on the wrapper, and md5 comparison proves nothing — the structural
  verify script is the acceptance test.
- Keep the proven bitstream pair (M0 below) as the fallback and do not delete it.

*Falsification, pre-registered:* success = post-route driver is `BUFG*` **and** the
per-POR both-die re-anchor rate rises materially above the 5/16 baseline over ≥12 PORs.
If the driver is a BUFG and the rate does **not** move, the lottery is not
capture-clock skew on this vehicle and M1 should be reverted to the proven build.

### M2 — Put the bounded-retry orchestrator on the critical path, and gate it on delivery `[BAR 1]`

*Justification:* highest value per unit of risk in this entire document, and it is
script-only. `pynq_host/scripts/kr260_eth_bringup_pair.sh` **already** implements
`MAX_TRIES=8` retry ("each retry re-runs winscan = a fresh eye"), but the 08-13
harness (`imp/hw_gate/tl035_ab.sh:105-113`) does a **single-shot** concurrent bring-up
and never calls it. Every lottery number in §4 was measured with retry switched off.

*Work:* (a) route all run paths through `kr260_eth_bringup_pair.sh`; (b) extend its
accept test from "both dies RE-ANCHORED" to "both dies RE-ANCHORED **and** a short
write→read-back delivery probe is byte-exact" — because `reanchored=1` + `FCSM=4` do
**not** imply a good eye (TL-031, and demonstrated 08-07). This is the software
equivalent of the TL-031 eye-qualification metric and needs no rebuild.

*Effort:* ~0.5 day. *Risk:* **LOW** — no netlist, no new RTL, fully reversible.

### M3 — Make the one real silent-loss path detectable, and mandate the check `[BAR 3]`

*Justification:* TL-005/TL-007's synth-B backstop returns **OKAY** for a write that
may never have landed. The registry says so plainly: *"OKAY masks the lost write-ack —
sound only for a data_id-routing corruption where DATA already landed."* That is
genuine silent data loss, and under bar 3 it cannot ship **undetected**. It does not
need an RTL fix, because the event is already recorded.

*Work:* after every experiment run, read witness `0x21F8` (marker `0xB5`) and treat
**bit8 (synth-B fired) or bit10 (stall-stuck)** as *run invalid, data suspect*. Add it
to the run harness as a hard post-condition. Two supporting rules:
- **Do NOT use Region F `0x21E0` for this.** TL-039/TL-040 plus the harness's own
  liveness probe ("stall bits NEVER moved under active write load … treat the sampler
  as DEAD") make `0xad800000` ambiguous between "healthy" and "not sampling". A
  never-driven B produces no stall, no wedge and no resp_err **by construction**.
- Always verify **die_b-locally**, never by reading back over the link.

*Effort:* ~2 h. *Risk:* **LOW** (read-only APB, no netlist).

### M4 — Re-green the FIFO regression suites `[BAR 3]`

*Justification:* TL-033 is the registry's only silent-corruption-class item. Per C4 its
guard **is** in shipping RTL — but its non-vacuity A/B (`make noguard`, which proves the
guard is load-bearing by failing without it) is **not currently passing**, so the guard
is unverified in either direction. That is the one place where bar 3 currently has no
live regression.

*Work:* land the drafted `test_43` probe fix (`packet_word_length` →
`u_fifo_ctrl.write_packet_word_length_r`) and the `fifo_rx_twin2` rename
(`packet_active_r` → `read_packet_active_r`); re-run `fifo_rx_phantom_pop`,
`fifo_rx_randinit`, `fifo_rx_twin2` and the `noguard` A/B.

*Effort:* **< 1 h.** *Risk:* **LOW** (test-only).

The HW-proven pair is **already built and preserved**, and this must not be lost:

| die_b | `imp/fpga/output/kr260-eth-chiplet-flip.a2lonly-28409f5/tidelink.bin` | `13573e46c3b27bb6b03b41b2ce730aa8` |

Provenance is clean and reproducible: `source_commit 5d58c2a3…`, `git_dirty: false`,

## 3. RECOVERY STORY

### The ladder — always take the cheapest rung that works

| L | Action | Command | Cost | Bench trip? |
|---|---|---|---|---|
| **L0** | Retry bring-up | `MAX_TRIES=8 bash pynq_host/scripts/kr260_eth_bringup_pair.sh` | ~15 s/try | no |
| **L1** | Re-load PL | `fpgautil` on the board | ~30 s | no |
| **L2** | JTAG POR | `~/bin/kpor kr260-01\|kr260-02 --wait` **on mapstone-dev** (or `pynq_host/scripts/weekend/por_recover.sh`) | ~45–90 s | no |
| **L3** | PARK | `MAX_POR=3` exhausted → `ALERT_<target>.txt` written | — | **yes** |

**L3 has never been reached.** Zero `PARK_*` / `ALERT_*` markers exist anywhere in the
tree. All 8 in-run wedge recoveries in the 08-13 campaign logged
`RECOVERED (ping+ssh up)` — **8/8**.

### Per failure mode

| Failure mode | Symptom you will see | Cheapest action | Bench trip? |
|---|---|---|---|
| Bring-up lottery miss | `fcsm=2`, `crack_seen=0`, or `LINK UP but NOT RE-ANCHORED — Marginal-eye lottery; RETRY the bring-up` | **L0** | no |
| Bad-eye link (up but marginal) | `fcsm=4` + re-anchored, but the delivery probe is not byte-exact; drops appear as all-zeros | **L0** (re-bring-up = fresh winscan) | no |
| TL-042 / TL-035 bus wedge | die_a `ssh` hangs then dies ~60 s; `/dev/mem` read of `0x21E0` returns `UNREADABLE`; harness rc `124` | **L2** | no |
| TL-009 sustained-write wedge | die_a unreachable after ~4–50 writes; `0x21F8` bit8/bit10 set | **L2**, then **L0** | no |
| Synth-B fired (silent lost write) | `0x21F8` bit8 = 1 while the PS saw OKAY | **invalidate the run**, then **L0** | no |
| PS wedge from a bad address poke | ssh dies immediately after the access | **L2** | no |
| Operator ran `sudo reboot` | board never comes back on the network | **L2** (JTAG POR only — `reboot` wedges a KR260) | no |
| PL reloaded on a live link | peer die wedges | **L2** on both dies | no |
| L2 fails 3× | `PARK_kr260_0N` marker + `Manual bench attention required` | escalate | **YES** |

**MVP verdict on bar 2: PASSED.** Every known failure mode terminates at L2 or below,
and L2 is remote. The only bench-trip path is L3, which has never fired in any recorded
run. **There is no known failure mode with no recovery short of a bench trip.**

### Operator restrictions that prevent the avoidable wedges

These are not bugs to fix — they are address hazards to write down:

- eth-chiplet APB is `0x4_0000_0000 + SoC`, i.e. **`0x2E032xxx`**. **`0x8403_xxxx` is
  UNDECODED and hard-wedges the PS** — this is what produced the retracted
  "rig eye degraded" story.
- **Never read `0x21AC` / `0x21B0` / `0x21B4`** — they hard-stall the CPU.
- **Never hand-drive the `0x208` triplet** — wedges the PS, and is unnecessary.
- **Never reload the PL on a live link.** **Never `sudo reboot` a KR260.**
- **Do not run `errinject` during an experiment.** It is a deliberate injector at
  `0x2E03_003C`; a valid AW byte-0 inject wedged die_a **8/8**.

## 4. THE RELIABILITY NUMBER

**The honest headline: single-digit-to-mid-teens sample sizes, measured with bring-up
retry switched OFF.** A 20-run overnight campaign was launched 2026-08-13 20:30 Z
(`imp/hw_gate/overnight/driver.log`) and is the first sample large enough to put an
interval on any of this. This section is written so those cells can be replaced.

### Bring-up, eth-chiplet two-board pair — `n = 16` runs / 32 die bring-ups

Each run directory in `imp/hw_gate/**` is **exactly one** bring-up attempt
(`tl035_ab.sh:105-113` has no retry loop).

| Metric | Result | n |
|---|---|---|
| Both dies reach `fcsm=4` | **15/16 = 94 %** | 16 runs |
| Both dies **RE-ANCHORED** (the harness's own M1 bar) | **5/16 = 31 %** | 16 runs |
| Per-die re-anchor | **15/32 = 47 %** | 32 dies |
| ILA sessions needing ≥2 inner tries | **4/4** | 4 sessions |

The single `fcsm=4` miss is `imp/hw_gate/tl035_tl042/04_bringup_a.log:17-18`
(`fcsm=2 … crack_seen=0`), which is the VOID run.

**With retry (M2), the composite is what matters.** At the observed per-attempt
both-die re-anchor rate *p* = 0.31, `MAX_TRIES=8` gives
`1 − (1−p)^8 = 1 − 0.69^8 ≈ 95 %`; at the `fcsm=4` bar (*p* = 0.94) it is
effectively 100 %. **Update *p* from the overnight campaign and re-evaluate — the
formula, not the number, is the deliverable here.**

### Delivery, eth-chiplet two-board pair

200-beat adversarial soak (seed `0xC0FFEE`, win=16), verified die_b-locally:

| Build | md5 | byte-exact | n |
|---|---|---|---|
| **baseline** (`a2lonly-28409f5`) | `9eadebb8…` | **7/8** | 8 |
| tl035 (`.tl033`) | `8947a50d…` | **4/5** | 5 |
| TL-042 candidate (rejected) | `0366c344…` | **0/2** | 2 |

Pre-inject localmem verify, baseline: **4/5** at 16/16.
**die_a wedges on a valid AW byte-0 inject: 8/8 — deterministic.**

### Numbers that must NOT be pooled into the above

- **30,500 byte-exact packets, 0 wedges (2026-07-23)** — this is the
  **`kr260-pair-onchip`** vehicle (two dies in **one** bitstream, one board, no
  ribbon), *not* the eth-chiplet pair. `n = 1` session, and its **SHA is
  unrecoverable** (`docs_site/build_registry.md:272`), so it is unreproducible and
  unbisectable. It also proves FIFO/FCSM/credit stability, **not** PHY stability.
- **2576/2576 byte-exact across 2 good-eye bring-ups (2026-08-08)** — correct vehicle,
  but `n = 2` bring-ups, and it is the *conditional* rate given a good eye, not the
  unconditional rate.
- **"128/128"** — **no surviving artefact.** `docs/BUILD_REGISTRY.yaml:161`: "128/128,
  16/16 and 11/11 have no surviving artefact."
- **"0/16 single peer write, all 16 runs"** — instrument artifact. See **C3**.

### What can honestly be claimed today

> On the KR260 eth-chiplet pair, a *single-shot* bring-up reaches link-up in 15 of 16
> attempts and reaches the full re-anchored state in 5 of 16. Given a good bring-up,
> the data plane delivers byte-exact in 7 of 8 measured 200-beat soaks, and has run
> 2576 consecutive byte-exact writes without a wedge. Bring-up retry is available and
> was not enabled during these measurements. All sample sizes are ≤16; a 20-run
> campaign is in flight.

### Explicitly deferred — with the rationale to defend it

**TL-042 / TL-035 — the bus wedge. DEFER.**
> The candidate fix was rejected on hardware for cause: it reused `synth_b_pending` as
> its release lever, and that signal is itself a term of `wr_hold_clr`, so firing the
> new arm *disabled* the TL-002 data-phase protection and dropped delivery from 16/16
> to 4/16. A correct fix must key on the consequence (sustained PS-facing stall), not
> on an intermediate signal the wedge suppresses — that is the whole point of the
> TL-042 bug class — and it needs a three-part test (hold escapes, `synth_b_pending`
> clears, *and* a subsequent normal write lands byte-exact) that does not exist yet.
> That is not one week's work done safely.
>
> **What could go wrong:** on a marginal eye, a real link bit error can trigger the
> same wedge a deliberate inject does. If that happens mid-experiment, die_a's PS
> hangs and the run is lost. **Mitigation:** it costs one remote JTAG POR (~90 s), it
> is loud rather than silent, and M2's delivery probe rejects the marginal eyes that
> make bit errors likely in the first place. Two of the three backstops on this path
> have now been *measured* not to arm, so shipping a third un-measured one is the
> higher risk.

**TL-037 AXI firewall / timeout. DEFER — but it is the best next investment.**
> It converts "PS hard-hang, JTAG-POR required" into "DECERR returned, Linux survives".
> That is a survivability upgrade worth more than any single RTL fix on this list —
> but it is a block-design change on the FPGA only, it does nothing for the ASIC, and
> it is a mitigation, not a root-cause fix. It does not fit safely in one week and it
> is not needed to meet bar 2, because JTAG POR is already remote.

**TL-032 calibrator wrap-stitch. DEFER *as a change to the shipping build*.**
> It is sim-proven, non-vacuous, and it removes a deterministic ~2–3/16 contributor to
> the drop lottery — but it is **not** in the HW-proven bitstream and has never been
> validated on hardware. Do not stack two unvalidated netlist changes (TL-032 and M1)
> into one week. **If** M1's rebuild happens anyway, TL-032 rides along for free since
> it is already on HEAD — in which case say plainly that the day-4 A/B is testing
> *both*, and that a null result cannot separate them.

**TL-031 eye-qualification metric in RTL. DEFER.**
> M2's post-bring-up delivery probe is the same idea in software, at zero netlist risk.
> Build the RTL metric only if the software probe proves too slow or too coarse.

**TL-028 RX word-clock `create_generated_clock` on the FPGA. DEFER.**
> Leverage is low: the word clock is ~195 kHz on KR260 with microseconds of slack, and
> the on-chip vehicle omits it too yet is lottery-free. Its value is diagnostic
> (it makes the B-return path STA-visible), not functional. Note the same report shows
> **8998 register pins with no clock** from the undeclared per-lane RX word clocks —
> real hygiene debt, but not this week's problem.

**Everything ASIC-line (TL-006 flist, TL-018/019/020), PTP (TL-010/TL-041), PHY BIST
(TL-011), TideChart (TL-025/TL-034). DEFER.**
> None of them affect whether the FPGA research vehicle comes up and moves bytes.
> TL-041 needs David's signature before any PTP claim is made, because a
> behaviour-changing fix to `servo_locked` reached both the shipping FPGA and the
> tapeout netlist inside a commit headed "No functional intent" — that is an audit-trail
> problem, not a functional one, and it is cheap to close but must not be closed silently.
