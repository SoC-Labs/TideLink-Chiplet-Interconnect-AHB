# TL-042 HW run #1 — VOID (2026-08-13 19:44Z)

Evidence: `imp/hw_gate/tl035_tl042/`. Predictions: `PREREG_TL042_HW_2026_08_13.md`.

## Verdict: this run tests NOTHING about TL-042. Do not cite it either way.

The link never came up on die_a, so the experiment never started. Recorded in
full because an undocumented void run is how a false conclusion gets built later
— `errinject_rc=2` sitting in a log with no context reads as "the fix failed".

## Instrument state (checked BEFORE the result, which is why this was caught)

Provenance was good — the deploy itself is sound:
- die_a md5 `0366c344cce3622ea937c6f8b292cadd` (FIXED image) — verified on-board
- die_b md5 `13573e46c3b27bb6b03b41b2ce730aa8` (BASELINE, byte-identical to the
  pre-fix runs — the fix is die_a-only, deliberately, so this stays a
  single-variable experiment)
- Both PL loads reported success; AFI width fix PASS on both (32-bit ports)

Then bring-up failed:

| die | cal_done | fcsm | cr_seen | crack_seen | result |
|-----|----------|------|---------|------------|--------|
| die_a | 1 | **2** | 1 | **0** | NOT converged (want fcsm=4) |
| die_b | 1 | 4 | 1 | 1 | LINK UP but **NOT RE-ANCHORED** after 12s |

die_b's own bring-up script printed the diagnosis:
**"Marginal-eye lottery; RETRY the bring-up (both dies)."**

## Why each prediction is UNTESTED (not refuted)

- **P1 (no wedge on errinject).** `errinject_rc=2` was produced against a DOWN
  link. The TL-042 mechanism is a `wr_hold_r` deadlock on an AHB write that
  reaches XHB500; with fcsm=2 there is no data path to exercise it. The rc says
  nothing about `wr_hold_r`.
- **P2 (128/128 delivery).** Never ran. Step 6 aborted by design:
  "ABORT: link not FCSM=4 ... Refusing to peer-access a down link (wedge risk)."
- **P3 (no spurious B).** Never exercised.

## Two readings that must NOT be mistaken for signal

1. `die_b LOCALMEM: VERIFY 0/16 byte-exact ... got 0x00000000` — this is the
   **pre-inject** read. die_b was already all-zeros BEFORE anything was injected,
   consistent with the link being down, not with a write being dropped.
2. Region F `0xad800000` "ALL CLEAN" on both dies. The harness itself flags this
   as meaningless: its liveness probe reported **"stall bits NEVER moved under
   active write load ... Treat the sampler as DEAD (TL-039/TL-040): every
   all-clean Region F read is MEANINGLESS, including TL-009's 0xad800000."**
   This is the same instrument defect that produced the retracted "rig eye
   degraded" narrative. It is not evidence of "no wedge".

## Was this caused by the fix?

Not established either way by this run, and it must not be assumed. Two facts
bear on it, both recorded BEFORE the run:

- The routed timing report for this build shows 8 failing hold endpoints. NONE are
  in the changed logic (`u_tidelink/u_master`).
  ⚠ **CORRECTED 2026-08-13.** An earlier revision of this file said those 8 were
  in `phy/gpio/gpiorx_*` (RX capture) and `u_rmii_to_mii`, and called them "the
  known placement-varying hold race behind the bring-up lottery". BOTH HALVES WERE
  WRONG. Re-extracted by pairing each `Slack (VIOLATED)` to its own `Source:`
  (the original extraction listed Source/Destination lines from the Min-Delay
  section WITHOUT checking which paths were actually violated): all 8 are
  `phy/gpio/gpiotx_N/g_pad_iob.io_pad_q_reg` — TX-FORWARD pads, path group
  `pad_clk_tx_fwd`, an artifact of `set_output_delay -min -20.000` in the target
  XDC. The RX capture domain PASSES in this same report (`pad_clk_rx`
  WNS +0.273 / WHS +0.055, 0 failing endpoints).
  Consequence: this report is NOT evidence for an RX-capture explanation of the
  bring-up lottery. The lottery may still be a capture-clock problem — see
  `fpga/docs/KR260_CAPTURE_CLOCK_TREE.md` on the fanout-372 capture net split
  across two BUFGCEs with 5.360 vs 6.113 ns insertion — but that is a structure
  STA does not flag, and it must be argued from the netlist, not from this table.
- The TL-042 fix is a 65536-cycle timeout on an already-stuck hold. It cannot
  plausibly affect training/CRACK, which is where this failed (fcsm=2,
  crack_seen=0).

**But plausibility is not evidence.** The discriminator is a BASELINE-ARM CONTROL
run under the identical protocol: `tl_arm_baseline.bin` on die_a, same POR /
load / AFI / bring-up sequence, same number of attempts. If baseline also
lotteries at a similar rate, the fix is exonerated on bring-up; if baseline comes
up reliably and the fixed arm does not, the fix is implicated and must be
investigated before any commit.

## Protocol for the retries (stated in advance, to keep this honest)

Bring-up is a PRECONDITION, not the dependent variable, so retrying until it
converges is legitimate. Two rules make it not p-hacking:
1. The SAME retry protocol and attempt budget applies to BOTH arms.
2. Every attempt is reported, including the failures — the bring-up success rate
   is itself a reported number, not a filter applied until the answer is liked.

Retrying until the *errinject* result looks favourable would be invalid and is
explicitly not what is being done here.
