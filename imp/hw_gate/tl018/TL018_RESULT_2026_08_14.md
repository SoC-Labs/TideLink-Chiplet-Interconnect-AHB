**Date:** 2026-08-14 · **Tree:** `nanosoc-ethernet-chiplet/tidelink` @ `e21e274`,
branch `integ/tidelink-consolidated-2026-08-07` · **Sim:** VCS, `source ./set_env.sh`

## 0. Verdict up front

The claim is **TRUE and understated**, but the registry's *framing* of it is **STALE**.

* Link CRC checking is really off on all five AXI data-plane FC nodes of the
  **shipping FPGA line**, and it is off in the **built bitstream IP**, not just in
  source. **MEASURED.**
* It is **ON** on the ASIC line, on both V1 flists, and on the two non-AXI nodes
  (`_5`, `_6`) of the FPGA line. **MEASURED.**
* It is a **runtime register**, not a compile-time default. One APB write per node.
  No RTL change, no netlist change, no tapeout risk. **MEASURED.**
* The documented *reason* it ships off — "saving 2 bytes per long packet
  (~9-20% bandwidth)", `docs/REGISTER_MAP.md:491-494` — **is factually wrong for this
  RTL**. The CRC bytes are on the wire either way; the bit only gates the RX
  comparison. Enabling checking costs **zero** bandwidth and **zero** clean-path
  latency. **MEASURED.**
* **The registry's `decision_needed: "David: ratify ASIC CRC reset value (on vs
  off)"` is stale. David ratified it — CRC ON — on 2026-07-21.** TL-018 is not an
  open design question; it is an **incomplete implementation of an approved
  decision**, caused by a stale flist premise. §5. **MEASURED.**

**Recommended severity: `high` on the FPGA line** (registry says `medium`) — but for
a sharper reason than the sign-off ledger gives, and with an ASIC caveat the current
entry conflates. §7.

**One thing the ledger's "cheapest path" gets wrong:** enabling CRC is cheap in
*silicon cost* and **not** cheap in *risk*. CRC-on has never passed traffic on any
hardware vehicle, and has twice been observed to park the FCSM in `SEND_NACK`. §6.

## 3. What CRC-off actually leaves open — concrete modes

Wire format (`docs/CRC_ROOTCAUSE.md:57-66`, cross-checked against the RTL):

```
byte 0      data_id                       <- ECC-protected (SEC-DED), NOT CRC
byte 1..2   word_count                    <- ECC-protected, NOT CRC
byte 3      ECC over the 24-bit header
byte 4      ll.data[7:0]  = FC pkt num    <- CRC + sequence check
byte 5..N   ll.data[..:8] = app payload   <- CRC ONLY. NOTHING ELSE.
byte N+1/2  CRC-16
```

`WlinkGenericFCSM.v:668` — `rx_crc_computed_crcgen_io_in = auto_rx_in_data`, i.e. the
CRC covers `ll.data` and nothing else. **MEASURED.**

| corrupted byte | protection with CRC **off** | outcome |
|---|---|---|
| **0** `data_id` | header ECC only | Single-bit flips are *corrected* (TL-006's `_T` fix). Anything ECC misses makes the packet not-a-data-packet → **silent drop**. CRC is gated on `data_id == swi_data_id_1`, so **CRC neither helps nor hurts this byte** — it is out of scope for TL-018. |
| **1-2** `word_count` | header ECC only | same — out of scope for TL-018 (this is TL-038's class). |
| **4** `pktnum` | sequence check `isNotExpPacket` | **Detected either way** → NACK → replay. CRC adds nothing. |
| **5..N** app payload | **none** | **SILENT.** No counter, no NACK, no replay, no error upstream. |

So TL-018's true blast radius is precisely the **application payload of all five AXI
channels**, and there it is total:

| node | what byte 5..N *is* | consequence of a silent flip |
|---|---|---|
| **W** 0x81 | AXI **write data** | wrong word committed to peer memory; master told the write succeeded. **MEASURED** §4. |
| **AW** 0x80 | AXI **write address** | write lands at the **wrong address**. INFERRED (same code path; not injected this session). |
| **AR** 0x83 | AXI **read address** | read returns the **wrong location's** data. INFERRED. |
| **R** 0x84 | AXI **read data** | wrong value returned to the master. INFERRED. |
| **B** 0x82 | BID / BRESP | wrong response id — also Fix-K's hazard-list wedge class. **MEASURED** §4. |

### 3.1 A corollary that matters more than it looks

With checking off, `crc_corrupt` is forced 0, so `crc_errors` at
`0x1020/0x1120/0x1220/0x1320/0x1420` is **pinned at 0 by construction**. INFERRED
from the RTL, and consistent with `cov_injector_liveness.py:11-14`.

`docs/reference/TIDELINK_BRINGUP_USER_GUIDE.md:305` step 12 checks
*"FC TideLink CRC clean @ 0x44031720 = 0 both sides"* — that is `0x1720`, the
**sideband** node (`FCSM_6`), the one node that already has checking on. **The
bring-up checklist's "CRC clean" tick says nothing whatsoever about the AXI data
plane.** Any campaign that read an AXI node's `crc_errors == 0` as evidence of a
clean data path was reading a dead instrument — the same failure mode as the 08-13
dead Region-F sampler.

## 5. Root cause of TL-018 — the registry framing is stale

The registry says:

```yaml
decision_needed: "David: ratify ASIC CRC reset value (on vs off). SW-recoverable either way."
```

**That decision was already taken, thirteen months of project-time ago in commit
terms.** `ac7dee8` (2026-07-21), *"fix(fc): re-enable link-layer CRC by POR default
(WlinkGenericFCSM_6)"*:

> **DECISION (David, 2026-07-21): root-cause the June disable and re-enable.**
> […] the 2026-06-14 "header-CRC fails on good DATA" was almost certainly **REAL
> corruption** on the marginal 4-lane 0xE4 2-beat DATA eye at 6.25 MHz, correctly
> caught by the CRC — **NOT a false fire**. […] Disabling CRC hid real corruption.

The implementation flipped exactly **one** file — `WlinkGenericFCSM_6.v` — on this
stated premise:

> This is the ONLY line that still shipped CRC-disabled — **FCSM 0-5 already default
> enabled via `deps/`.**

**That premise was already false when it was written.** `c2b2d51` (2026-07-04),

re-pointed FCSM 0-4 to CRC-off local overrides **17 days earlier**.
`git log -L 745,750:src/rtl/local_overrides/WlinkGenericFCSM.v` returns exactly one
commit — `c2b2d51` — and the line has never been touched since. **MEASURED.**

So: **an approved "turn CRC on" decision was implemented against a stale flist
premise, and landed on the one node that did not need it while missing the five that
did.** This is the same class of error the brief sent me to look for in TL-033 and
TL-027 — a registry entry describing a world that has moved — except here the stale

Two supporting notes:

## 6. Cost of turning it ON

### 6.1 Bandwidth: **zero**. The register-map justification is wrong. MEASURED.

`docs/REGISTER_MAP.md:491-494` justifies shipping the check off:

> *"SM Control bit [16] (`disable_crc`) in each FC node disables CRC checking, saving
> 2 bytes per long packet (~9-20% bandwidth depending on payload size). At GPIO speeds
> the bit error rate is negligible, making CRC overhead unnecessary."*

**The bit does not gate transmission.** Structurally verified:

* `grep disable_crc` on `Wlink{Tx,Rx}LinkLayer.v` (both `deps` and `local_overrides`)
  → **zero hits**. The link layers have no such input.
* `WlinkGenericFCSM.v:663` — `assign auto_tx_out_crc = bundleOut_0_crc_crcgen_io_out;`
  unconditional.
* `WlinkTxLinkLayer.v:54` — packet extent is `topIndex = auto_in_word_count + 16'h6`;
  `:115,:140` place the CRC bytes at `word_count + 4/5`. Nothing in the length or
  placement depends on `disable_crc`.

The two CRC bytes are on the wire whether or not anybody looks at them. **Enabling
checking costs 0% bandwidth.** The stated reason the check ships off does not exist —
and note the second half of that sentence ("BER is negligible") is a claim about the
6.25 MHz Z2 GPIO link, whereas the V1 ASIC target is a 100 MHz GPIO PHY, 16× faster.

### 6.2 Clean-path latency: **zero**. INFERRED (structural).

`rx_crc_computed_crcgen` is a combinational unrolled XOR tree evaluated every packet
regardless; `disable_crc` gates only the comparison term in `crc_corrupt`. No extra
cycle, no extra stage. Nothing in `imp/hw_gate/` or the 07-31 throughput work measures
a CRC-on-vs-off throughput delta — **because there is no mechanism for one on the
clean path.** I found no such measurement and am not manufacturing one.

Do **not** quote the sim wall-times in §4.2 (3.35 s vs 4.22 s) as a throughput cost:
that delta is one NACK+replay round on a deliberately corrupted packet, i.e. the
error path, plus test-harness time.

### 6.3 Error path: real, and this is the whole risk. MEASURED (history).

A detected error asserts `crc_corrupt` → `valid_rx_pkt_crc_err` → `crcCorruptSeen`
(`FCSM.v:242`) → latches `send_nack_req` (`:402`) → FCSM state 7 → NACK → replay. It
also suppresses enqueue (`pkt_is_data_pkt = _crc_corrupt_T_2 & ~crc_corrupt`, `:204`),
so a detected packet is dropped, not merely counted.

**CRC-on has never been shown passing traffic on any hardware vehicle.** Three data
points, none of them a pass:

1. **2026-06-14, Z2 pair** (`34b6a90`) — the only time an enabled CRC ran on a live
   link. `crc_errors @0x44031720` saturated **429 → 65535 per burst**, FCSM parked in
   `SEND_NACK`, **zero data delivery**. The 2026-07-21 root cause concluded this was
   the CRC **correctly catching real corruption** on the marginal 4-lane `0xE4` eye.
2. **`docs/BUG_REGISTRY.yaml:216`**, TL-001 `refuted:` list —
   *"CRC-enable (both-die SEND_NACK wedge)"*. A CRC-enable was tried as a TL-001
   mitigation and wedged both dies. No retained log.
3. **2026-07-30, KR260 eth-chiplet** (`6d85c68`, CRC-ON compiled into both bitstreams)
   — `docs/HANDOVER_KR260_FCSM_BRINGUP.md:82` **"FALSIFIED — link still down"**. The
   link never left FCSM state 0 for an unrelated `role_locked` reason, so this run
   carries **no information** either way.

**The correct reading is not "CRC-on is broken".** It is: *on a marginal eye, enabling
CRC converts silent corruption into a visible stall.* For a research chip that is the
right trade — but it is a trade, and with TL-037 (no AXI firewall/timeout anywhere on
the path) a stall on the eth-chiplet means **ssh dead, JTAG POR only**.

Mitigations already present on the FPGA line, and absent on the ASIC line:

* `WlinkGenericFCSM.v:331-339` — the TL-033 state-7 watchdog. The `else` branch is the
  **default**, so the pre-TL-033 sticky `socl_l7_real_crc_seen` kill (which
  `docs/CRC_ROOTCAUSE.md:275-279` and `ac7dee8` both flag as the danger of enabling)
  is **already fixed** here. It has a documented known limit (`:325-329`): it breaks a
  `send_nack_req`-stuck case but not a pure emit-starvation stall. **MEASURED.**
* `deps/…/WlinkGenericFCSM.v` has **no watchdog and no `socl_` hook at all** (TL-019).
  So the ASIC ships CRC-on with none of the FPGA's state-7 protection. That is an
  ASIC-line concern that belongs in TL-019, not TL-018.
* The I5 outstanding-response backstop bounds a non-converging replay to
  `HRESP=ERROR` — `test_axi_b_persistent_eye_bounded` already covers exactly the
  "every replay re-corrupted" case.

## 7. Severity

**Registry: `medium`. Sign-off ledger: should be `high`. I agree with `high` for the
FPGA line — but the entry needs splitting, and the ledger's reasoning needs one
correction.**

**Why `high`:**

1. It is on the **shipping vehicle**, in the **built bitstream** (§1.4), on **all five**
   AXI channels.
2. The failure is **silent and total** on the app payload — measured, not asserted:
   memory holds the wrong word, every observable including Region-F reads healthy (§4.2).
3. It **invalidates measurements**, which is the product of a research chip. A wedge
   is honest; a wrong number that looks right is not.
4. The documented rationale for it is **false** (§6.1) — there is no cost being bought.
5. It is an **incomplete implementation of an approved decision** (§5), not an open
   question. Nothing is waiting on a design call.
6. It silently **disables an instrument**: the AXI `crc_errors` counters are pinned at
   0, and the bring-up checklist's "CRC clean" tick reads a different node (§3.1).

**Why not `rank1_critical`:** runtime-recoverable with one APB write per node; no
netlist change; no tapeout risk; **ASIC unaffected**.

**Split the entry.** TL-018 currently conflates two things:

* **TL-018 (FPGA):** five AXI nodes ship CRC-off → silent payload corruption.
  → **`high`**, status `root_caused` → fix available and runtime (§8).
* **TL-018b / fold into TL-019 (ASIC):** the shipping ASIC combination — CRC-on **+**
  FCSM-`deps` (no `socl_` recovery, no state-7 watchdog) **+** ECC-local — had never
  been co-simulated. That is a genuine residual, but it is about the *recovery* path,
  not the CRC reset value. Note the `ASIC_MIRROR=1` / `make gaps_ecc_asic` target now
  exists and covers ECC-restore under exactly that combination.
  → **`medium`**, and it is a TL-019 consequence.

**One correction to the ledger.** Its cheapest-path column reads *"Decide the reset
value deliberately, or make the bring-up script set CTRL bit[16]. SW-recoverable
either way."* The first half is stale (§5 — it was decided). The second half is right
but **understates the risk**: it reads as free, and §6.3 shows it is not. Recommending
a blanket default-on without a hardware soak would repeat the TL-042 pattern exactly —
sim-proven, deployed, rejected on hardware.

## 8. What I changed (NOT committed)

### 8.1 Runtime fix — `pynq_host/scripts/kr260_eth_bringup.py`

New `--crc-check {report,on,off}`, **default `report`**, plus `crc_state()`,
`print_crc_state()`, `set_crc_check()`, and an AXI-CRC block in the read-only
`--status` path.

* **`report` (default)** — reads `SM_CONTROL[16]` and `crc_errors` for all five AXI
  nodes and prints them, with an explicit "pinned 0: checking off" annotation so the
  counter is never mistaken for evidence. **Pure reads, zero risk.** This alone fixes
  the half of TL-018 that is unambiguously free: *the state is currently invisible on
  every bring-up path.*
* **`on`** — read-modify-write clears bit[16] on all five, **with per-node readback
  verify**. RMW is required: `ack_dly_count[15:8]` is HW-validated at 4 and a blind
  write would silently re-time the link.
* **`off`** — restores the shipping default.

Sequenced as **step 4b**: after `FCSM==4` (LINK_IDLE), before any data traffic.
CR/CRACK are short packets carrying no CRC, so nothing earlier is affected, and the
first DATA packet is the first one that can be checked — the ordering
`docs/CRC_ROOTCAUSE.md:288-295` recommends.

**Why the default is `report` and not `on`.** CRC-on has never passed traffic on
hardware and has twice parked the FCSM in `SEND_NACK` (§6.3). Defaulting it on from a
sim result would be the TL-042 mistake. `report` takes the free win now and puts the
enable one flag away for the soak that must ratify it.

**preserves** `link_en_wait`/`ack_dly_count` (`0x10708 ↔ 0x00708`, matching the POR
value measured in `docs/CRC_ROOTCAUSE.md:106`). `py_compile` clean.

## 10. What would actually close TL-018

Not a sim result — sim is already unambiguous. The open question is entirely
hardware, and it is narrow:

1. Bring both dies up as usual, then `--crc-check report` on each. Expect
   `checking=OFF` ×5. *(Verify the instrument before the DUT.)*
2. Re-bring-up with `--crc-check on`; confirm the readback took on all five, both dies.
3. Run the existing byte-exact delivery soak. **Log `crc_errors` AND `fcsm` together,
   sampled continuously** — `crc_errors` alone is a weak instrument (it is force-zeroed
   whenever the demetted app enable is low, `FCSM.v:761-763`), so an enable dip erases
   the evidence.
4. The pre-registered discriminator:
   * `crc_errors == 0` **and** delivery unchanged → the eye is clean at this rate;
     land the §9 RTL revert.
   * `crc_errors > 0` **and** delivery still byte-exact → the CRC is catching real
     corruption **and the replay is converging**. This is the *best* outcome: it means
     the FPGA line has been silently committing bad data at a measurable rate, and now
     is not. Quantify the rate — it is also the BER metric TL-031 asks for, for free.
   * `crc_errors` saturates and the link stalls → the eye is too marginal at this rate
     (the 2026-06-14 result). **Do not conclude "CRC is broken."** Conclude the link
     was delivering corrupt data all along. Then fix the eye (TL-009) or drop the rate,
     and keep `--crc-check off` as the documented, *deliberate*, temporary escape —
     with the AXI `crc_errors` limitation written into the bring-up guide so nobody
     reads `0x1720` as data-plane health again.

Pair it with **TL-037** (an AXI firewall/timeout). With a firewall in place, the worst
case of enabling CRC degrades from "ssh dead, JTAG POR" to "a failed transaction" —
which is what makes the enable safe to default.
